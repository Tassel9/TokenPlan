# 单意图与多意图：100 条自然表达诊断对照

本轮记录历史单意图基线与同样本多标签对照。要检验的是：多意图能否保留额外明确诉求，同时不误拆常见单诉求；不能先假定多意图一定更好。

更新（2026-10-04）：默认链路已改为[单个业务路由直接派发，orchestrate 请求由 Supervisor 拆解并记录主诉求](intent-context-boundaries.md)。当前模型与端到端结果见[新链路评测记录](orchestrate-routing-evaluation-20261004.md)。下方表格保留更早版本的冻结结果；原评测脚本仍显式保留历史单 / 多标签协议。

职责修正（2026-10-04）：要求代购、退款提交、退订或修改账户的输入可以保留，但咨询 Agent 的正确行为是说明限制并询问是否转人工。[咨询职责预期 v2](../evaluation/fixtures/intent_natural_consultation_v2.json) 保留原 100 条输入和话题标签，增加每条的行为预期；其中 29 条先询问人工，8 条先回答咨询再询问人工。不能把标签识别正确等同于操作完成，也不能把询问转人工等同于已经转人工。

## 样本与标注边界

数据在 [intent_natural_comparison_v1.json](../evaluation/fixtures/intent_natural_comparison_v1.json)。100 条唯一输入，74 条单标签、16 条双标签、10 条范围外或需澄清输入。切片分别为常规单诉求 34、原因与背景混合的单诉求 26、多轮当前单诉求 14、相关多诉求 16、范围判断 10。这个比例是诊断设计，不是线上流量比例。

这些句子和预期标签由助手在查看对照预测前拟定，是人工构造草案，不是客服原始工单，也不是独立人工金标。每条保留标注理由。自然程度待用户审核，业务标签待独立复核；`production_evidence=false`。两条技术问题的叙述方式参考公开用户报告：[调用逐渐变慢](https://github.com/deepseek-ai/DeepSeek-V3/issues/269)、[旧登录问题解决后报告当前故障](https://github.com/deepseek-ai/DeepSeek-V3/issues/233)，均已改写，不把它们冒称 TokenPlan 真实工单。

## 公平基线

[SingleIntentRecognizer](../backend/core/single_intent_recognizer.py) 与显式注入的历史 `IntentRecognizer` 共享模型、完整 13 标签树、业务标签定义、原文证据校验、上下文预算、改写、安全降级和融合策略。唯一实验变量是标签基数要求：单意图独立请求模型选择当前主诉求，工具 schema 和本地校验均限制一个标签。不是先跑多意图再截断，也没有移除单意图的历史或故意使用较弱模型。

单意图优先当前明确重点，没有指定时选原文最先提出的独立诉求。每条另有 `primary_intents`，用于评估主诉求覆盖，避免只用“必须返回两个标签”的集合全对指标制造基线必败。两套方案都可在范围或指代不确定时澄清，不强制选一个标签。

基线可通过已有注入点用于本地实验，无需改变生产默认：

```python
from core.single_intent_recognizer import SingleIntentRecognizer
from core.intent_pipeline import IntentRecognitionPipeline

baseline = SingleIntentRecognizer(context, embedding_index=embedding_index)
pipeline = IntentRecognitionPipeline(context, recognizer=baseline)
outcome = await pipeline.recognize(query, history=history, case_state=case_state)
# IntentOrchestrator(..., intent_recognizer=baseline) 也支持此实例。
```

这是一套与当前实现匹配的单意图基线，不是对 intent-fusion 外部仓库的完整复刻。两者同用当前项目的融合门限，以隔离“是否支持多个标签”这一变量。

## 运行与指标

```powershell
.\.venv-win\Scripts\python.exe evaluation/compare_single_multi_intent.py --mode contract
.\.venv-win\Scripts\python.exe evaluation/compare_single_multi_intent.py --mode live --repeats 2 --output evaluation/reports/intent_natural_100_single_multi_split_v2_run01.json
```

报告和逐次观测日志使用新文件名写入，不覆盖已有结果。示例新路径使用后，重新运行应改成 `run02`。每轮同样 100 条；两轮最多 400 次识别尝试，歧义上下文在识别前停止，校验重试另计；独立样本数仍为 100。上下文每条只整理一次，双方及识别重复轮次共用结果；该协议检查识别层稳定性，不是独立重复整条流水线。

主比较采用与现有调度门禁一致的**可路由标签**：只有 `status=ready` 才计入；任何整体澄清都不视作已派发。报告另外保留模型提议、融合单标签确认、原文证据、验证错误、状态、模型及代码哈希，便于查清“语义没识别到”与“门禁拦住”两类原因。不会执行购买、退款或其他业务工具。

- 集合与范围全对：标签集合一致，而且范围状态一致的观测数 / 总观测数。故障降级产生空标签不冒充正确拒识。
- 主诉求覆盖：识别到预标主诉求的观测数 / 总观测数；多诉求切片中单意图也可以得满分。
- 错加标签与漏标签：分别计数预测减金标、金标减预测；不能只报召回率。
- 单诉求误拆：单标签输入被返回多个标签的数量，以及被附加错误标签的数量。
- 分切片和配对：单诉求两者谁更好、多诉求实际多识别了什么、哪些情况反而退步；两轮输出不一致单独报告。
- P50/P95：串行交替顺序、双方已预热相同整理后文本向量；总耗时含共用的上下文成本，另报排除该成本的纯识别耗时。不是冷启动或业务端到端延迟。

固定融合权重 0.10，确认门限 0.70，低分门限 0.40，两套完全相同。温度 0，关闭思考，同等请求 token 上限、校验重试次数和上下文。数据与识别器源码的摘要在运行前固定，运行中变化则拒绝生成完整对照报告。不根据本次错误调 prompt 或门限再重跑并包装成盲测。

统计检验仅用第一轮的每条输入，不把两轮重复当作独立样本；人工构造病例也不是随机流量样本，因此显著性不能外推生产。报告中的多意图占比敏感性只是假设情景，不声称实际占比。双标签样本上单意图的召回上限本来就是 50%，超过这个上限**不自动证明多意图值得部署**。

## 如何决策

先查看真实或独立复核的单诉求表现，尤其是误拆与错加；再看相关多诉求中新增结果是否正确，是否因为一个低置信度次要标签阻断主诉求。最后结合真实多诉求占比、额外轮次、错误动作代价与端到端耗时做决定。

如果增益只来自这 16 条人为选取的双标签输入，而常见单诉求反而更差，就应优先单意图；如果不损害单诉求且确实减少相关诉求遗漏，可以保留受限多意图，但仍需要真实脱敏工单或独立业务复核支持。识别正确也不等于退款、发票等任务最终完成。

## 拆分前实测：有覆盖收益，也有单诉求退步

2026-10-03 使用 `deepseek-v4-flash` 完成两轮。两轮各 100 个同样输入，每套共 200 次观测，独立输入仍为 100 个。两轮各切片的集合与范围全对数量一致：

| 每轮切片 | 单意图 | 多意图 |
| --- | --- | --- |
| 常规单诉求，34 条 | 33/34 | 33/34 |
| 含背景的单诉求，26 条 | 24/26 | 23/26 |
| 多轮当前单诉求，14 条 | 13/14 | 12/14 |
| 单诉求合计，74 条 | 70/74，94.59% | 68/74，91.89% |
| 双诉求完整覆盖，16 条 | 0/16（能力限制） | 16/16 |
| 范围外或需澄清，10 条 | 10/10 | 10/10 |
| 总体，100 条 | 80/100 | 94/100 |

为了避免把“只能返回一个标签”混成错误理解，另外检查了双诉求原始输出：**单意图在 16 条中每次均选中一个正确诉求，没有错选到金标之外的标签**。预先声明的“按原文重点或最先请求选择主诉求”覆盖为两轮合计 26/32，多意图 32/32；单意图有时选了另一项同样真实的诉求，不应把这种顺序偏差夸成完全识别失败。

多意图的双诉求新增标签两轮合计 32 个正确、0 个错误；但单诉求中额外确认了 2 个错误支付标签，并少路由了 2 个本可单独确认的退款标签。这里的 2 次分别是同一案例的两轮重复，不是两个独立案例。

两条多意图特有退步均重复出现：

1. `goal-03`：“钱扣了两次，把多扣的那笔退回来吧”。单意图只识别退款；多意图把原因再标成支付问题，并以高分确认，造成额外标签。按本草案“只标当前独立交付”的口径算错；若业务要求必然先查账，也应在独立标注复核中说明，不得看完预测再改成双标签报胜。
2. `turn-03`：“多的那笔退回来就行”，历史说明重复扣款。单意图确认退款；多意图虽确认退款（融合分 0.855674），又附加支付标签（0.574561，处于澄清区），最终全局门禁返回澄清，没有路由退款。链路是“背景被拆成次要标签 → 次要标签不确定 → 阻断已有明确主诉求”。

两套都失败的四条单诉求为 `goal-01`（付费升级后权益未生效）、`goal-25`（退出离职成员设备且席位不动）、`plain-30`（已申请的票未发到邮箱）、`turn-10`（已解决故障后的报错文案建议）。前者还存在相邻标签解释空间，其余主要是提议正确但融合分不足，需另行定位，不能把共有问题都归因于多意图。

两轮合计的识别延迟：单意图 P50 1218 ms、P95 1500 ms；多意图 P50 1203 ms、P95 1516 ms。这个差距很小，且只测暖缓存的识别，不足以宣称明显提速。单意图 2 个输入两轮结果不一致（均在双诉求中的选项变化），多意图 0 个；多意图 1 次结构校验重试，两套树通道不可用均为 0。
