## 一次对话结束后怎么保存

1. 只有成功提交的完整用户/助手轮次进入 Outbox。Redis 用原有 Lua 将对话、CaseState、更新任务和 Pending 一起提交。任务带原始消息、表达时间、用户、会话、轮次、实际 workspace 和操作目标；抽取使用的消息 ID 由服务根据稳定 job ID 和角色计算。助手原话可作为助手建议的来源，摘要不进入证据池。
2. 默认累计十轮后抽取；不足十轮时，最后一轮任务入队后空闲 120 秒也会处理。“记住/记下来/remember”提前处理。成功发布压缩视图后，移出的未处理轮次标记为可处理；输入仍来自 Outbox，不从摘要补造。正常关闭在既有十秒预算内尝试剩余批次，未完成的 Redis 来源留给重启恢复。关闭时间不保证一定抽取成功。
3. 批次按完整轮次和 Token 预算切分。默认模型输入总预算 12000 Token；正文、消息 ID、提示词和旧记忆都计入。优先移除辅助上下文和旧记忆，单轮仍超预算时保留失败来源，不截断半个问答。一批最多参考四条较早的原始消息及十条相关已发布旧记忆。
4. 一次模型调用产生最多 24 条候选，输出上限 4096 Token。每条按一个主题保存正文，可以包含相关原因和条件。模型选择类型、归属、作用域并逐字引用输入消息。
5. 程序检查字段、类型、原文引用、来源角色、实际作用域、敏感内容和保存策略。用户事实/偏好/计划需用户证据；助手建议必须有助手证据并标成“助手曾建议”；接受助手方案需同时引用用户接受原话和方案。新记忆必须含新消息证据，旧上下文/旧记忆不能单独触发新增。明显的假设、当轮篇幅要求、业务当前状态和覆盖系统规则的内容被拦截。原文匹配证明出处，不能证明陈述真实，也不能完全保证模型的语义归类正确。
6. 校验结果先存入 Redis。每条候选分别按正文召回最多五条相同用户、作用域、类型和归属的有效旧记忆，同批较早候选也通过向量排序提供最多五条比较对象。过期、撤回、被替换及 Pending 屏蔽的正文不作为比较对象。精确正文先做哈希检查；已知单值投影发生变化时普通抽取直接跳过；其余候选由模型批量判断 `ADD/SKIP`。
7. 同一作用域内重复已有记忆项直接跳过；普通抽取仅改变已有单值或已知期限也跳过。不同事情、新原因或新条件独立新增，不保存 `comparison_relation`、`compared_memory_id`，不建立记忆关系。类别相同不等于同一件事，例如开发系统和常用语言均为事实，仍可分别保存。不同作用域分别保存，明确更正使用单独流程。程序要求每条候选恰好一项决策，`ADD` 不得带旧目标 ID，`SKIP` 只能引用该候选的比较对象供程序校验；新投影或首次明确期限不能被误丢弃。判断输入使用同一 12000 Token 上限；整条超限时先减少相关对象，再分组，正文和引用不截断；仍超限则保留失败来源。
8. 只将需要新增的正文批量向量化、写入 `user_memories_v1`，CAS 发布 `memory-manifest`。重复候选不生成正文、向量、确认事件，也不更新旧五字段投影或有效期。任务判断缓存只保存候选 ID、`ADD/SKIP` 和跳过目标 ID，供重试及删除保护使用；不是持久记忆关系，缓存随原批次回收。发布回调核对当前有效记录、发布记录和 Pending，变化则在最多四次尝试内重新判断。已识别为跳过的迟到候选受目标删除时间约束；旧版确认数据仍能读取和清理。首次竞争仍可能重复调用模型，跨库发布不是分布式事务。

```mermaid
flowchart LR
    A[完整轮次成功提交] --> B[Redis Outbox 与 Pending]
    B --> C[十轮 / 空闲 / 压缩 / 记住]
    C --> D[原话 + 有限上下文 + 相关旧记忆]
    D --> E[一次模型抽取]
    E --> F[来源与保存规则校验]
    F --> G[缓存结果 / 精确去重]
    G --> R[逐候选召回 / 新增或跳过]
    R --> H[新增正文 BGE 向量 / Chroma 写入 / CAS 发布]
    H --> I[完成 Outbox]
```

## 每条存什么

正文是一条可独立理解的主题记忆。类型为 `user_fact`、`user_preference`、`user_plan`、`project_decision` 或 `assistant_advice`，分别表示陈述、偏好、计划、决策和历史建议。

元信息包含服务生成的 ID、用户、角色归属、用户/会话/workspace 作用域、观察时间、创建时间、有效期、原始消息 ID、带角色的引用、来源 job ID 和正文哈希。Chroma metadata 内的多来源信息是有长度限制的 JSON 字符串。

旧五个字段成为可选投影，由同一份已接受正文派生；不运行第二个抽取器。相同正文带多个投影时合并为一条记录，例如 Windows 和 VS Code 同时对应 OS 与 IDE。固定字段的当前值仍遵守明确替换规则；普通抽取不改变已有单值。显式替换的旧正文及此前版本留下的矛盾正文可保留为历史，不作为当前单值注入。

同用户、作用域、类型、归属和标准化正文做哈希去重，候选生成后还进行独立的新增/跳过判断。同义改写判断为 `SKIP` 后不生成任何新记忆记录，也不续期；新信息判断为 `ADD` 后保存独立正文及原文证据。旧版 `CONFIRM` 仅用于兼容已有历史有效期，不再生成新确认。向量召回筛选比较对象，模型判断是否同一件事；有限召回和模型误判仍可能漏去重或误丢信息，不能宣称全库语义唯一。

默认保留期：通用用户事实/项目决策 180 天，偏好 365 天，计划/助手建议 30 天，可通过配置调整。五个固定字段维持原有 365/180 天政策。模型只可引用原文明写的 `YYYY-MM-DD` 截止日期，不能编造日期。未知的相对期限使用策略 TTL。

## 用户提问后怎么检索和注入

1. `chat_service.py` 先取得近期原话和 CaseState，执行一次有来源校验的 Query 补全。补全后的同一 `effective_query` 同时用于召回和意图识别；歧义或校验失败时不猜测召回。不同委派任务再以各自的问题独立召回，写入只读快照；原始用户消息继续作为写入与审计依据。调用 MemoryManager 的底层兼容入口仍可使用有来源的辅助 Query。详见[共用 Query 补全](shared-query-memory-recall.md)。
2. 按用户、会话/workspace、生效时间、TTL、撤回/替换标记和 Pending 筛选已发布记录。BGE/Chroma 每条 Query 召回最多二十条，沿用余弦距离 ≤0.58；关键词重合仅给这些语义候选排序加权，不能召回向量候选之外的内容。相似度不是事实可信度。
3. 校验新旧发布清单与 Pending 前后版本，变化则重读。查询完成后再检查有效期。最多注入五条完整主题正文，带类型、user/assistant 归属、观察时间和 ID；当前请求优先。两项全局表达偏好继续直接注入，其余旧字段提供兼容召回。全部 `LongTermMemoryContext` 默认不超过 800 Token；超预算时丢弃完整记录，不截断归属标记。
4. Agent 提示词明确长期记忆仅作为背景。助手建议不能当成用户选择或已完成业务操作。空 Query 不召回非全局记忆；检索失败只读取仍有效的表达偏好，不全量注入。

“我当前这个套餐和新出的哪个好”可以召回月付/年付、预算和使用需求等背景。当前账户套餐、付款/退款结果与新产品权益仍由业务查询和产品知识获取。

当前 API 的 user_id 校验方式没有在这次改造中更换。测试验证的是存储与检索的用户作用域隔离，不能据此宣称已经新增身份认证。

## 明确修改或忘记

自然语言请求只有唯一主题/ID 时执行；目标不唯一就通过原有 WAITING_USER 路径澄清，列出候选 ID。workspace 由当前任务实际实体提供，模型不能自造 ID。

“忘记这个项目的所有记忆”只处理指定 workspace 的正文及未删除的替换历史，保留其他项目和全局偏好；缺少唯一 workspace 时澄清。“不要忘记/删除”不会走撤回快路径。带项目范围的系统/工具变更也不会自动覆盖全局五字段设置。

用户提交明确请求时先原子发布 Pending：通用正文及对应旧字段一起被屏蔽。明确单值修改/撤回走规则快路径；其他 ID 更新由一次抽取产生有新证据的替代记录，再发布 `supersede` 标记。旧正文保留为替换历史，但不进入当前召回。一次 ID 更新不得用助手建议替换用户事实，替换内容需匹配目标类型和作用域。

删除清理正文、证据副本、向量、兼容旧字段和抽取缓存，保留无正文、无原值的删除边界。边界包含时间、目标 ID、正文哈希与来源 ID，迟到任务仍受其约束。物理删除或缓存清理失败时重试继续，Pending 不提前清除；后台启动及默认每 300 秒清理过期记录并重试已发布清单中的垃圾 ID。

自然语言操作复用持久 Outbox。`MemoryManager.list_memories(..., include_history=True)`、`update_memory(...)`、`forget_memory(...)` 是内部调用方法；作用域通过 conv_id/workspace_id 传入，删除不会跨用户。未删除的替换历史可查，删除/到期正文不能再查。这些内部方法失败会向调用者抛出异常，调用者应重试；它们没有新 HTTP 管理端点。

独立原始会话归档仍按原会话 TTL 保留；删除长期记忆不等于删除聊天记录。历史原话只辅助理解，不独立产生新事实，原删除来源的迟到任务会被边界挡住。用户在删除之后明确重新表达，可以产生新的记忆。

## 配置、迁移与回退

完整变量见 [configuration.md](configuration.md)。应用默认新引擎；直接构造 MemoryManager 仍默认 `legacy`，兼容既有调用方和测试。运行时一个任务只由选定引擎抽取，不同时运行两个模型抽取器。设置 `LONG_TERM_MEMORY_ENGINE=legacy` 后重启应用，可回到五字段读取；新阶段的字段修改/忘记同步到旧投影，因此回退不会恢复已忘记的五字段偏好。旧引擎不读取通用主题库。

旧库不会自动改写，也没有对现有用户数据执行迁移。迁移命令默认只读预览：

```powershell
$env:PYTHONPATH = "backend"
.venv-win/Scripts/python.exe -X utf8 -m memory.migrate_memory_flow
# 停止流量、处理未完成 Outbox 后，显式导入；源库保留。
.venv-win/Scripts/python.exe -X utf8 -m memory.migrate_memory_flow --apply
```

可加 `--user-id` 限制范围。导入仅取当前有效的旧字段值，保留确认事件实际决定的 TTL，不刷新时间；过期、撤回、被替换值不导成当前记录。原文不能恢复时标记 `legacy_reference`、保留旧来源 ID，evidence 留空，不伪造引用。重复运行不重复导入，已有删除边界阻止旧数据恢复。迁移只支持版本化旧事实事件，不能凭旧整份画像补造原始来源。

SQLite 是显式离线适配：正文持久化到 SQLite，但后台待处理任务和抽取缓存仍在进程内。它不具备 Redis Outbox 的崩溃恢复保证，也不作为 Redis/Chroma 故障时的自动降级。
