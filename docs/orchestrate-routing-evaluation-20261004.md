# 2026-10-04 单路由、复合诉求与端到端评测

本次将“一个主业务意图后统一进入 Supervisor 检查”改为“普通业务路由直接派发，`orchestrate` 请求进入 Supervisor 拆解”。主诉求、逐项融合、阶段隔离已实现。真实模型评测显示语义集合完全正确从 90/100 到 92/100，端到端任务通过从 14/28 到 15/28；LLM 调用与 Token 的下降更明显，整体成功率改善仍小。当前主要遗留问题是多轮理解和分数门禁，这些离线结果不代表生产成功率。

## 实现范围

- 识别器只输出一个业务标签或 `orchestrate`，编排路由独立于 13 个业务标签。
- 普通业务请求按父领域直接派发。复合请求由 Supervisor 拆解并记录 `primary_intent_id`：明确重点优先，否则按原文诉求顺序选择；置信度不表示重要程度。
- 拆解后的每项诉求用自身原文证据计算 Embedding，再与自身 LLM 分数融合。独立的未确认诉求单独澄清；已确认诉求均回答完后保留结果。不确定的前置诉求阻止后续依赖。
- 后续轮次使用冻结后的执行提示词与 Tool schema，不再允许重写分析。`orchestrate` 不进入后续业务候选；规范化编号时，主诉求、派发和人工确认引用同步映射。
- Agent 的问题正文从其绑定诉求的已校验原文证据组装，避免委派文本夹带其他事项。显式顺序请求每阶段只允许一条消息、一个意图和 `all_success`。
- Agent 保持咨询及受控只读查询职责。代购、退款提交、退订、开票或账户修改要求需询问是否由人工办理，不宣称实际操作或转接完成。

## 数据与口径

对照使用修改前和最终修改后两个独立代码快照。报告逐文件记录 backend Python SHA256，并检查评测期间代码没有变化。最终工作区也与最终快照逐文件核对；快照是本地备份，不是已经提交的 Git 版本。

模型均为 `deepseek-v4-flash`，Embedding 为固定 revision 的 `BAAI/bge-base-zh-v1.5`。Embedding 权重 `0.10`、确认门限 `0.70`、低分门限 `0.40` 保持不变。业务定义仍为 13 个，新方案增加一个控制路由定义向量。

原 100 条语义样本与金标、原 28 个端到端任务及判据没有改动。语义模型只接收当前输入、受控上下文和公共标签定义；预期标签与切片只在模型输出后评分。

语义主指标是**融合后业务标签集合及范围均与预期完全一致的样本数 / 100**。旧方案计入首轮 Supervisor 检查结果，新方案普通路由直接评分、编排路由计入拆解及逐项融合结果。它包含真实识别与首轮规划调用，不包含领域 Agent 执行和最终答复。

端到端主指标是**确定性判据与 LLM Judge 同时通过的任务数 / 28**。任务包含 1–3 轮消息，不能将接口无异常、最终出现一个关键词或已识别标签直接算作任务成功。Judge 与执行模型同源，仍有判断偏差。

最终方案在 16 条多诉求样本中均选择 `orchestrate`；74 条单诉求中没有选择编排入口。随后逐项融合保留完整集合的为 15/16，路由正确不代表所有子诉求最终通过门禁。

逐条对照有 4 条改善（`plain-30`、`goal-25`、`related-10`、`related-11`），2 条退化（`turn-13`、`related-05`）。对同一组开发诊断样本的结果，不能推断独立未知流量上的稳定增益。

`related-05`：“团队再加两个席位，新增的钱开在我们公司抬头下”。模型拆解出了权益与发票两个正确标签，但发票证据的 Embedding 为 `0.285082`、LLM 为 `0.72`，融合为 `0.676508`，落在澄清区间。它是正确提议被门禁阻断，不能归因于模型没识别发票，也不能为了这一个样本直接降低全局门限。

其他失败涉及：升级付款后权益仍未生效的相邻标签混淆；“那笔也开到公司抬头吧”的指代歧义；退款进度和反馈追问的低分；“再加一点”的上下文引用校验失败；“把它停了”的对象范围未正确判定。单业务路由漏判为普通请求时，后续 Agent 也不会自动补出第二个业务领域。

## 验证边界与复现

代码回归为 `661 passed`。其中新增的 12 个专项回归覆盖控制路由、当前原文证据、普通路由直接派发、主诉求及会话保存、逐项融合、独立部分完成、低置信前置阻断、编号合并、冻结后的原生 Tool Call 和委派正文隔离。Mock 证明契约和控制流，模型及端到端报告另外证明这些具体样本的表现。

端到端实际运行 ChatService、识别、Agent、RAG/只读业务工具、回复护栏及会话提交，使用隔离 SQLite 和嵌入式 Chroma，数据是测试语料与隔离记录。宿主机没有可用的 Redis 服务，本次将真实 `RedisSessionStore` 注入 fakeredis 客户端；Redis 网络基础设施被模拟。HTTP 传输、真实部署、长期记忆队列消费者、线上并发和真实账户操作不在本轮评测范围。

最终对照的修改前和最终版本各运行一次，`k=1`；没有随机交叉重复实验。开发中在同一组诊断样本上看过中间版本的错误并修复，因此最终对照也不构成独立盲测。不同评测进程存在并行运行，缓存和模型服务负载会影响延迟；P50/P95 仅记录本次观测，不是延迟保证。Token 口径为输入、输出及缓存输入合计；端到端 Judge 调用不计入链路用量，Token 减少不等于已核实的账单降幅。
