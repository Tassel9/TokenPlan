# 长期记忆与意图识别复用统一 Query

2026-10-17：默认聊天入口先补全当前问题，再让长期记忆召回和意图识别使用同一个已校验结果。

## 执行顺序

1. 读取短期对话和 CaseState，完成已有的跨会话咨询恢复；若咨询对象存在歧义，先澄清。
2. `IntentOrchestrator.prepare_query_context()` 调用原流水线的 `prepare_query()`，生成并校验 `PreparedQueryContext`。
3. 当结果为 `not_needed` 或 `resolved` 时，用其中的 `effective_query` 检索长期记忆。完整问题保留原句，不强制改写。
4. 将同一个 `PreparedQueryContext` 放入本轮编排请求；编排器调用 `recognize_prepared()`，意图 LLM 与意图 Embedding 均使用这份 `effective_query`，不再调用补全模型。
5. 召回的长期记忆进入后续任务上下文，不反过来参与本轮补全，避免循环依赖。

用户原文继续保存在 `Request.message` 和 `original_query` 中，用于原文证据校验、请求控制、审计和记忆写入。补全内容不能当作用户新声明的事实。

## 异常和兼容边界

- 补全歧义、引用校验失败或补全服务不可用时，跳过长期记忆召回，将同一结果交回现有识别门禁处理；不退回原句猜测召回，也不重新补全。
- 问候、人工转接和密钥拦截保留原有模型短路行为。
- 复用结果必须对应当前请求原文；原文不一致会被拒绝。
- 直接调用 `IntentOrchestrator.run()` 且未传入补全结果时，仍保留原来的自动补全入口。
- 显式注入旧版一体化 Supervisor、未提供预处理方法的测试或第三方适配器，继续沿用原入口；统一复用针对默认 `IntentRecognitionPipeline` 主链路。
- 应用层补全耗时仍计入 `query_context_ms` 和原有编排总耗时；聊天请求的端到端 Trace 继续记录实际墙钟耗时。


## 验证范围

`tests/test_shared_query_memory_recall.py` 覆盖一次补全、同一结果复用、完整问题、歧义、无效引用、补全服务异常、记忆服务异常、取消传播、原文不匹配、控制消息和直接编排入口。本地版本另覆盖 `mem0_flow` 的相同边界及会话/工作区参数。

这些回归验证调用顺序和输入边界，不代表真实模型的语义准确率、线上记忆命中率或生产效果提升。

本次针对性回归共 102 项通过，包含 10 项新增复用测试，以及现有上下文、短路、跨会话咨询和 Trace 回归；未调用真实模型或业务服务。
